 PART 1: THE PITCH — "Why This Matters" (2–3 minutes)
================================================================================

[START WITH THE PROBLEM — Relatable scenario]

SAY:
"Let me start with a real problem we face in microservices architecture.

Imagine two teams working on related services:
- Team A runs a User Service with a field called 'name'
- Team B runs an Order Service that calls Team A's API and expects 'name'

One day, Team A does a harmless refactor — renames 'name' to 'fullName'.
Team A's own tests pass. They deploy. Everything looks fine.

But Team B's service breaks in production. Silently. No one knows until
customers start complaining.

This is the #1 integration problem in microservices: services break each
other without knowing."

[PAUSE — let it sink in]

SAY:
"What if we could catch that breaking change at build time — automatically,
in the CI pipeline, BEFORE anyone deploys anything?

That's exactly what this project does."

[TRANSITION TO SOLUTION]

SAY:
"I built an end-to-end contract testing automation system with three layers:

1. CONTRACT TESTING — YAML files that define 'when consumer sends X,
   provider MUST return Y'. If the provider breaks this contract,
   the build fails. Deployment is blocked.

2. AI AGENT — A Python tool with 12 intelligent modules that reads the
   API's OpenAPI specification and automatically generates these contract
   files, detects when contracts drift out of sync, performs root cause
   analysis on failures, checks backward compatibility on every merge
   request, and sends rich notifications to Microsoft Teams with action
   buttons.

3. CI/CD PIPELINE — A GitLab pipeline with 14 jobs across 5 stages that
   runs all of this automatically on every push. Breaking changes
   never reach production. The team is always informed."

 PART 2: THE EXPLANATION — "How It Works" (5–7 minutes)
================================================================================

[SHOW THE ARCHITECTURE — Use the README diagram or draw on whiteboard]

SAY:
"Let me walk you through how the pieces fit together."

--- COMPONENT 1: Provider API (User Service) ---

SAY:
"First, the Provider — this is a Spring Boot REST API running on port 8080.
It's a User Management service with 5 endpoints: GET all users, GET by ID,
POST create, PUT update, DELETE.

Key thing: it auto-generates an OpenAPI specification at /v3/api-docs.
This is the machine-readable description of the entire API — every endpoint,
every field, every data type. The AI Agent reads this."

Tech details (if asked):
- Spring Boot 3.3.8, Java 25 (Oracle LTS)
- springdoc-openapi 2.5.0 for auto-generating the spec
- Jakarta Validation for request validation
- In-memory store with 3 sample users

--- COMPONENT 2: Consumer API (Order Service) ---

SAY:
"Second, the Consumer — an Order Service on port 8081. It calls the Provider
to enrich orders with user information. When you fetch an order, it
internally calls GET /api/users/{userId} on the Provider.

This is the real dependency. If the Provider changes its response format,
the Consumer breaks. The Consumer has a UserDTO class that maps to the
Provider's response — this IS the contract dependency."

--- COMPONENT 3: Contract Files (The Agreement) ---

SAY:
"Third, the contracts — 12 YAML files that define expected request/response
pairs. We have both positive scenarios (5 happy-path contracts) AND negative
scenarios (7 error-handling contracts for 400 and 404 responses).

For example:"

[Show a contract file — should_return_user_by_id.yml]

SAY:
"This says: when you send GET /api/users/1, you MUST get back a 200
response with id, name, email, and role fields. The matchers section
uses regex to validate format without being brittle about exact values.

Spring Cloud Contract reads these YAML files and does two things:
1. On the PROVIDER side: auto-generates JUnit tests that call the real API
   and verify it matches the contract
2. On the CONSUMER side: generates WireMock stubs so the Consumer can test
   without needing the real Provider running"

--- COMPONENT 4: AI Agent (The Automation Brain) ---

SAY:
"Fourth — and this is where it gets interesting — the AI Agent.
It's a Python tool with 12 internal modules:

1.  spec_reader — fetches and parses the OpenAPI spec from the running Provider
2.  contract_generator — converts endpoints into SCC YAML contracts (happy path)
3.  negative_contract_generator — generates error scenario contracts (400, 404)
4.  drift_detector — compares existing contracts vs current API spec
5.  coverage_tracker — tracks coverage metrics and trends over time
6.  report_generator — produces health reports with coverage metrics
7.  root_cause_analyzer — AI explains WHAT failed, WHY, and HOW to fix
8.  backward_compatibility — detects breaking changes vs main branch baseline
9.  ci_config_generator — generates the entire GitLab CI pipeline YAML
10. notifier — sends Teams, Slack, GitLab Notes, and SMTP notifications
11. mr_creator — auto-creates Merge Requests with fixed contracts
12. mr_validator — posts validation summary as a comment on merge requests

And it has 103 pytest unit tests ensuring every module works correctly.

You run it with simple CLI commands:
  python main.py generate              → creates contract files
  python main.py generate --negative   → creates error scenario contracts
  python main.py drift                 → finds mismatches
  python main.py report                → health report
  python main.py fix --create-mr       → auto-fix + create merge request
  python main.py analyze               → root cause analysis on failures
  python main.py compat                → backward compatibility check
  python main.py dashboard             → starts the web dashboard on port 5050
  python main.py coverage              → coverage metrics and trends"

--- COMPONENT 5: CI/CD Pipeline ---

SAY:
"Finally, the GitLab CI pipeline — 14 jobs across 5 stages:

Stage 1 BUILD:  Compile both services + AI-generate contracts from spec
Stage 2 TEST:   Drift detection → backward compat → contract tests
Stage 3 REPORT: Summary + Teams/Slack notifications + RCA + MR comment
Stage 4 FIX:    Manual trigger — regenerate contracts + create MR
Stage 5 DEPLOY: Only runs if ALL tests pass + publishes dashboard to Pages

The logical flow is:
  1. First, BUILD generates contracts from the live OpenAPI spec
  2. Then, DRIFT CHECK runs — no point testing if contracts are stale
  3. Then, BACKWARD COMPAT — blocks if breaking changes found (MR only)
  4. Then, CONTRACT TESTS — verifies Provider against all 12 contracts
  5. Then, CONSUMER TESTS — verifies Consumer against WireMock stubs
  6. Finally, REPORT stage sends rich Teams notifications with:
     - Health status (HEALTHY/WARNING/CRITICAL)
     - Coverage metrics (12/12 contracts, 100% coverage)
     - Action buttons: View Dashboard, View Report, View Pipeline
  7. GitLab Pages publishes the dashboard for persistent access

Key features:
- If a contract test fails, deployment is BLOCKED.
- The team gets notified via Microsoft Teams with an Adaptive Card.
- On MRs, a backward compatibility checker blocks breaking changes.
- On failures, root cause analysis explains exactly what went wrong.
- A formatted validation summary is posted as a comment on the MR.
- And there's a one-click auto-fix that regenerates contracts and
  opens a Merge Request for review."

================================================================================
 POTENTIAL MANAGER QUESTIONS & ANSWERS
================================================================================

Q: "Why contract testing instead of integration testing?"
A: Integration tests require BOTH services running at the same time.
   Contract tests work independently — Provider tests against contracts,
   Consumer tests against stubs. Faster, more reliable, no flaky network.
   We get the same confidence as integration tests at the speed of unit tests.

Q: "What happens when someone adds a new endpoint?"
A: The AI Agent's drift detector catches it — reports "uncovered endpoint".
   Run `python main.py generate` to auto-create the contract. Or the
   auto-fix CI job can create a Merge Request automatically.

Q: "Can this scale to 50+ endpoints?"
A: Yes. The AI Agent reads the OpenAPI spec programmatically. Whether it's
   5 endpoints or 500, it generates contracts in seconds. Manual work = zero.

Q: "What's the CI pipeline time?"
A: Build + test + report takes about 3-4 minutes in GitLab CI. Maven caching
   makes subsequent runs faster.

Q: "How does the notification work?"
A: Four channels in priority order: Microsoft Teams webhook (primary —
   Adaptive Card with metrics and action buttons), GitLab Issue Notes
   (@mentions guarantee email delivery), Slack webhook, and direct SMTP.
   Each channel is independent — if one fails, the next is tried.
   The agent sends a single consolidated notification per pipeline run.

Q: "What if the contract test gives a false positive?"
A: Contracts use regex matchers for flexible validation — they check structure
   and format, not exact values. False positives are rare. If they happen,
   you update the contract YAML (takes 30 seconds).

Q: "Why Python for the AI Agent and not Java?"
A: Python is ideal for scripting, HTTP calls, and YAML manipulation.
   It keeps the agent lightweight and fast to iterate. The agent doesn't need
   Spring Boot's framework — it just reads specs and writes files.
   Plus it has pytest for fast, expressive unit testing (103 tests run in <5s).

Q: "Is this production-ready?"
A: The contract testing (Java/Spring Cloud Contract) and CI/CD pipeline are
   production-grade. The AI Agent is a developer tool — it generates files
   that go through normal code review (MR) before merging. The backward
   compatibility checker and root cause analyzer add enterprise-grade
   safety that prevents breaking changes from reaching production.

Q: "What about negative/error testing?"
A: The AI Agent generates both positive (200/201/204) AND negative (400/404)
   contracts. It tests that invalid requests return proper error responses
   with the correct status codes and error message format. This catches
   silent validation regressions that happy-path tests miss.

Q: "How does the dashboard work?"
A: It's a Flask web app on port 5050. It runs live Maven tests, shows
   real-time coverage metrics, displays drift detection results, and shows
   root cause analysis for any failures. In CI, it exports a static HTML
   snapshot published to GitLab Pages — accessible from Teams notification
   buttons via persistent URLs.

Q: "What's the backward compatibility checker?"
A: On every MR, it compares the current API spec against the main branch
   baseline. If you removed a field, changed a type, or deleted an endpoint,
   it blocks the merge with a clear explanation of what would break consumers.

Q: "How reliable is the AI Agent? How do you test it?"
A: 103 pytest unit tests across 10 test modules cover every module.
   Tests use mocks and fixtures to verify parsing logic, YAML generation,
   drift detection, notification formatting, and compatibility checking.
   All tests run in the CI pipeline before merge.

Q: "What's the View Dashboard / View Report button in Teams?"
A: They link to GitLab Pages — a persistent static site published from
   the CI pipeline. Unlike job artifact links (which expire or return 404),
   GitLab Pages URLs are always available. The dashboard shows the latest
   contract health status, and the report shows detailed findings.
